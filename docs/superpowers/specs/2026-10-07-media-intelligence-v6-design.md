# Media Intelligence v6 — архитектурная спецификация

Дата: 2026-10-07  
Статус: **утверждён для планирования реализации; реализация не начата**  
Основание: текущий `main` @ `d51e95a73d04342cc31a96b9ad629a3b0c66957a`

## 1. Цель

Media Intelligence v6 оптимизируется под реальный основной сценарий использования:

> **один фильм → один пользовательский отзыв → один разбор LLM → одна типизированная операция → одна минимальная пересборка → одна итоговая проверка → одно слияние**

Главная цель — **максимальное быстродействие без потери достигнутого качества анализа и рекомендаций, на текущей инфраструктуре, за счёт алгоритмической, логической, кодовой, стратегической и структурной оптимизации**.

Скорость не должна достигаться уменьшением объёма анализа или ослаблением гарантий. v6 должна устранять повторный ввод-вывод, повторные проходы LLM, ненужное признание данных устаревшими, лишние пересборки, лишние Git-транзакции и лишние холодные запуски CI.

LLM остаётся основным пользовательским интерфейсом. Сайт остаётся полноценным вторичным клиентом и визуальной оболочкой той же системы. Ветка GitHub `main` и основные Git/YAML-данные остаются единственным долговременным источником состояния.

## 2. Неподвижные качественные гарантии

v6 сохраняет сильные стороны v5.1:

- явные пользовательские сигналы важнее выведенных системой предположений;
- семантика произведения не выводится из отношения пользователя к нему;
- оценка и реакция пользователя не считаются доказательством объективных свойств произведения;
- семантический отпечаток строится только на контролируемом словаре;
- происхождение данных сохраняется;
- ранее выведенный результат не становится самостоятельным основанием для следующего вывода;
- явно указанное сходство — это сигнал о сходстве, а не предпочтение пользователя;
- различия между вкусами пары не скрываются усреднением;
- оценка кандидата остаётся качественной и не использует ложную точность в виде псевдовероятностей;
- неполнота данных и известные ограничения продолжают снижать уверенность вывода;
- свежие явные пользовательские сигналы важнее устаревшей выведенной интерпретации.

Любая оптимизация, нарушающая эти инварианты, не соответствует v6.

## 3. Сброс старой медиатеки

Перед переходом на v6 выполняется полный сброс активной медиатеки.

### 3.1 Человекочитаемый архив

До удаления активных данных создаётся один MD-архив всей текущей медиатеки: `docs/archive/media-library-before-v6-reset-2026-10-07.md`.

Архив содержит все существующие произведения. Для каждого произведения сохраняются только человечески полезные данные:

- название и год;
- статус просмотра;
- оценка;
- реакция;
- текстовый отзыв;
- явно высказанные причины/заметки;
- данные `partner` / `couple`, если они реально существуют.

Отдельно архивируются:

- явно заданные связи сходства между произведениями;
- названия существующих подборок.

Архив не содержит:

- внутренние идентификаторы произведений;
- идентификаторы внешнего поставщика данных;
- идентификаторы операций;
- технические контрольные хэши;
- семантические отпечатки;
- выведенные гипотезы;
- технические сведения о происхождении данных;
- состояние и этапы пилотного процесса;
- служебные данные CI и рабочей системы.

Архив является памяткой и чек-листом. Он **не является машиночитаемым источником восстановления**, не участвует во входных данных рекомендаций и не используется для анализа вкусов.

Архив генерируется детерминированным CLI-инструментом, а не вручную. Проверка полноты должна заново построить ожидаемый архив из текущих основных данных и сравнить его с зафиксированным MD-файлом. Простого сравнения количества произведений недостаточно. Деструктивный сброс разрешён только после успешной точной проверки.

### 3.2 Что очищается

После проверки архива активное состояние очищается:

- произведения в основных данных;
- подборки;
- связи сходства между произведениями;
- взаимодействия;
- старый пилот переоценки;
- выведенные предпочтения `primary`, `partner`, `couple`;
- рабочие артефакты, относящиеся только к старому пилоту.

### 3.3 Что сохраняется

Сохраняются:

- глобальные явно заданные предпочтения и правила;
- контролируемый словарь;
- схемы и код;
- логика рекомендаций и оценки кандидатов;
- Broker;
- Web/Pages;
- история Git.

Базовые данные Stage A перестают участвовать в рабочем расчёте. Если отдельные старые сценарии нужны для регрессионных проверок, они переносятся в специальные синтетические или эталонные тестовые наборы.

## 4. Старый процесс переоценки больше не используется в рабочей системе

После перехода на v6 старый процесс переоценки больше не является действующей возможностью системы.

Из рабочей системы и маршрутизации агента удаляются:

- `reserve_reassessment_session`;
- `complete_reassessment_item`;
- `close_reassessment_session`;
- `record_reassessment_modernization`;
- специальная оркестрация модернизации для пилота;
- специальные для пилота ветви транзакций, правил разрешённых путей и процессов GitHub Actions.

История остаётся в Git и исторических спецификациях.

Повторное прохождение старых фильмов идёт через MD-архив как нейтральный чек-лист: LLM показывает произведение без старой оценки и старого отзыва, чтобы не закреплять прежнее мнение, пользователь даёт свежий отзыв, после чего используется обычный путь записи v6.

## 5. Главная составная операция

v6 вводит основной путь обычной записи — `record_media_entry`.

Операция соответствует одному естественному человеческому событию о конкретном произведении.

Концептуальный состав запроса:

```text
schema_version
operation_id
idempotency_key

work_ref
create_if_missing

viewer_updates[]

creation_context?
  resolved_identity
  provider_identity
  minimum_metadata

semantic_snapshot?
  traits
  semantic_input_digest
  vocabulary_digest
  algorithm_version

preconditions
  expected_viewer_digest[target]?
```

Операция не превращается в универсальный механизм произвольных пакетных изменений. В неё не входят глобальный повторный анализ вкусов, несвязанные изменения сходства, изменения словаря и массовое обслуживание данных.

### 5.1 Быстрый путь для существующего произведения

Для существующего фильма обычный отзыв содержит только:

- ссылка на произведение;
- изменение пользовательских данных;
- ожидаемый контрольный хэш пользовательских данных.

Он не требует:

- обращение к внешнему поставщику данных;
- обновление метаданных;
- повторный расчёт семантики;
- старая процедура модернизации;
- глобальный повторный анализ вкусов.

### 5.2 Путь для нового произведения

Для нового фильма одна операция атомарно включает:

- однозначно определённая личность произведения;
- идентификатор внешнего поставщика;
- минимально необходимые фактические данные;
- семантический снимок, подготовленный LLM;
- пользовательские сигналы.

Последовательность `add → reread → semantics → feedback` не должна быть обычным путём.

Если произведение уже появилось до применения операции, устойчивый идентификатор используется для сопоставления вместо создания дубля.

## 6. Логические слои основных данных

Физически произведение может оставаться единым YAML-файлом, но логически состоит из независимых слоёв:

```text
Work
├── identity
├── metadata
├── semantics
└── viewer state
    ├── primary
    ├── partner
    └── direct couple/group evidence
```

Изменение одного слоя не делает остальные слои устаревшими автоматически.

## 7. Защита от устаревшего состояния

Для реального сценария использования v6 принимается важное ограничение: независимые отзывы не поступают одновременно из нескольких LLM, из LLM и сайта или из других клиентов. Поэтому система не проектируется вокруг параллельной очереди пользовательских записей.

При этом обычный отзыв больше не должен зависеть от контрольного хэша всего файла произведения.

Основная проверка перед записью:

```text
work identity
+ target
+ expected_viewer_digest(target)
```

Она нужна не для поддержки одновременного редактирования, а как защита от случайно устаревшего запроса, повторного запуска или изменения состояния между чтением и применением.

Типизированное намерение пользователя при применении всегда сверяется со свежим `main`; заранее подготовленный старый YAML-патч напрямую не применяется.

Идемпотентность и проверки контрольных хэшей остаются обязательной дешёвой защитой от повторной отправки, сбоя сети и ручного повторного запуска.

## 8. Идемпотентность

`operation_id` остаётся идентификатором конкретной попытки для аудита.

`idempotency_key` идентифицирует одно пользовательское событие.

Повтор одного и того же события не должен:

- создавать дубли в истории;
- увеличивать счётчик новых пользовательских сигналов;
- создавать дубликат произведения;
- повторять пересборку;
- создавать второй логический отзыв.

`no_change` является полноценным успешным результатом и не создаёт искусственную запись в истории.

## 9. Зависимости и определение необходимых пересборок

Доменная логика сначала сообщает, **что изменилось**, а инфраструктурный слой определяет, **что нужно пересчитать**.

Вводится явный `changed_domains`, например:

```text
work_identity
metadata
semantics
viewer.primary
viewer.partner
explicit_preferences.primary
similarity.primary
```

Затем детерминированный планировщик зависимостей строит `DirtyPlan` — список производных результатов, которые действительно нужно обновить.

Принцип:

> Доменная логика объявляет изменения; инфраструктура выводит из них необходимую пересборку.

Каждый затронутый производный результат пересобирается максимум один раз за операцию.

## 10. Контрольные хэши и доказуемое повторное использование

Логика контрольных хэшей становится отдельным доменным контрактом.

Минимально нужны:

- `compute_viewer_digest(work, target)`;
- `compute_metadata_digest(work)`;
- `compute_semantic_input_digest(...)`;
- `compute_profile_input_digest(repo, target)`;
- `compute_evidence_digest(repo, target)`.

Набор входов каждого контрольного хэша должен быть документирован и покрыт тестами, включая проверки того, что **не входит** в расчёт.

Общий принцип:

> **посчитать один раз и доказать, что результат можно использовать повторно**

Если контрольный хэш входных данных и версия алгоритма совпадают, повторное вычисление запрещено как ненужное.

## 11. Актуальность метаданных

Метаданные делятся минимум на три класса:

- данные, определяющие произведение;
- относительно постоянные факты;
- изменяющиеся показатели.

Для каждого класса действует отдельное правило актуальности.

Изменение популярности, числа голосов и похожих показателей внешнего поставщика не делает семантический отпечаток устаревшим.

Для отзыва о существующем произведении внешние обращения к поставщику данных отсутствуют.

Для нового произведения создание блокируют только данные, необходимые для надёжного определения произведения, и минимальный набор фактов для качественной семантики. Необязательные метаданные не блокируют пользовательский отзыв.

## 12. Семантический отпечаток

Ключ семантики определяется как:

```text
hash(
  semantic_input_projection
  + vocabulary_digest
  + semantic_algorithm_version
)
```

Оценка, реакция и отзыв пользователя, история, состояние пилота и показатели популярности внешнего поставщика не входят во входные данные семантики.

Если ключ совпадает, семантика используется повторно без нового прохода LLM.

### 12.1 Подготовка семантики на стороне LLM

Основная LLM, с которой разговаривает пользователь, подготавливает семантику нового или действительно изменившегося произведения один раз.

### 12.2 Проверка перед сохранением в репозитории

GitHub/Python не повторяют рассуждение LLM. Они детерминированно проверяют:

- схему;
- термины контролируемого словаря;
- ключ семантики;
- версии алгоритма и словаря;
- происхождение данных;
- отсутствие терминов пользовательской реакции в семантическом отпечатке произведения;
- согласованность идентичности произведения.

## 13. Устаревшие данные не блокируют отзыв

Устаревшие метаданные или семантика не блокируют отзыв пользователя о существующем произведении.

Пользовательские сигналы сохраняются независимо.

Обслуживание обновляет только действительно устаревший слой и только тогда, когда это требуется правилами.

## 14. Пересборка производных данных

`MutationPlan` v6 содержит изменения основных данных и `changed_domains`.

Отдельный слой зависимостей строит `DirtyPlan`.

Транзакция:

1. проверяет команду;
2. загружает текущее основное состояние;
3. проверяет точечные предварительные условия;
4. применяет все изменения основных данных в памяти;
5. определяет изменившиеся области;
6. определяет производные результаты, требующие обновления;
7. один раз пересобирает каждый нужный производный результат;
8. проверяет итоговое состояние репозитория;
9. записывает квитанцию операции;
10. создаёт коммит.

Между внутренними изменениями основных данных пересборки не выполняются.

На первом этапе v6 профиль по-прежнему полностью и детерминированно строится для конкретного затронутого пользователя. Сложный частичный пересчёт профиля не вводится без измеримого узкого места.

`media/generated/` остаётся версионируемым в Git, но пересборка выполняется строго по фактическим зависимостям.

## 15. Быстрый пользовательский путь через LLM

GitHub остаётся границей долговременного сохранения, но перестаёт определять задержку самого разговора.

Логические статусы:

```text
accepted_local
pending_persistence
authoritative
failed/conflicted
```

LLM может продолжать разговор после принятия и отправки операции, не ожидая слияния.

Слово «сохранено» допустимо только после подтверждённого состояния в `main`.

Если пользователь уточняет тот же фильм, пока предыдущая запись по нему ещё не подтверждена, разговор не блокируется: LLM сразу учитывает уточнение во временном состоянии текущей сессии. Но новая Git-операция по тому же произведению не отправляется, пока первая не станет `authoritative`. После подтверждения первой операции LLM читает свежий `viewer_digest` и отправляет накопленное уточнение как следующую обычную операцию. Редактирование уже отправленного request PR ради такого уточнения не является нормальным путём.

## 16. Учёт ещё не слитых изменений в текущем разговоре

Пока операция ожидает подтверждённого сохранения, текущий разговор с LLM может учитывать только явные пользовательские сигналы:

- статус просмотра;
- оценка;
- реакция;
- текстовый отзыв;
- другие явно выраженные сигналы.

Временный слой текущего разговора:

- не является второй БД;
- живёт только в текущем разговоре;
- после слияния заменяется состоянием из `main`;
- после ошибки или конфликта перестаёт считаться сохранённым;
- не содержит автоматически выведенных глобальных изменений профиля;
- может накапливать последующее уточнение того же произведения, пока первая операция ожидает подтверждения, но это уточнение отправляется в Git только после получения свежего состояния из `main`.

## 17. Компактный контекст для чтения

Добавляется компактный маршрут только для чтения `media_entry_context`.

Он возвращает минифицированный JSON с минимумом, необходимым для обработки обычного отзыва:

- данные, однозначно определяющие произведение;
- текущее пользовательское состояние;
- контрольный хэш пользовательского состояния;
- состояние актуальности метаданных;
- состояние и ключ семантики;
- необходимые фактические поля;
- текущий семантический отпечаток;
- состояние интереса.

Маршрут не возвращает полную историю, полный профиль, полный блок метаданных или другие поля, которые не нужны для текущего решения. Размер контролируется составом полей и при необходимости ограничением сериализованного JSON в байтах; жёсткий лимит по токенам не вводится, потому что он зависит от конкретного токенизатора.

Для простого отзыва LLM не должна последовательно читать индекс, файл произведения, профиль, словарь, документы состояния и старый контекст переоценки.

Контролируемый словарь читается только тогда, когда создаётся или меняется семантика.

## 18. Повторный анализ вкусов

Глубокий повторный анализ вкусов не входит в обязательный путь сохранения каждого отзыва.

Свежие явные пользовательские сигналы используются сразу.

Выведенные предпочтения остаются сохранённой интерпретацией, а не первичным источником истины.

### 18.1 Порог новых пользовательских сигналов

Настраиваемый порог; значение по умолчанию — **5**.

Одна единица новых данных:

- максимум +1 за одно содержательно изменившееся пользовательское событие по одному произведению;
- количество изменённых полей не увеличивает значение;
- повтор отправки, отсутствие изменений и изменение только метаданных не считаются;
- существенная последующая переоценка того же произведения может дать ещё +1.

Основой служит контрольная точка и контрольный хэш набора пользовательских сигналов, а не отдельный изменяемый счётчик.

### 18.2 Раздельные контрольные точки для пользователей

Контрольные точки независимы для:

- `primary`;
- `partner`.

`couple` не имеет отдельного автоматического счётчика. Перед решением, зависящим от вкусов пары, проверяется актуальность обоих индивидуальных профилей.

### 18.3 Обязательная проверка перед решениями, зависящими от вкуса

Проверка обязательна перед запросами, где ответ зависит от вкуса:

- рекомендация;
- рекомендация из уже известной библиотеки;
- сравнение кандидатов;
- оценка того, насколько подойдёт конкретный кандидат;
- рекомендация для пары;
- «подойдёт ли мне X?» и аналогичные запросы.

Простой поиск и фактические запросы повторный анализ вкусов не запускают.

Если число новых содержательных пользовательских сигналов достигло порога, LLM обязана сначала заново проанализировать вкус, а затем строить ответ, зависящий от предпочтений.

Новый выведенный профиль может использоваться как временное состояние текущего разговора до слияния. Контрольная точка в основных данных продвигается только после подтверждённого сохранения.

Результат повторного анализа сохраняется отдельной типизированной операцией `set_inferred_preferences`, а не через `record_media_entry`. Команда должна сохранять сам выведенный профиль и контрольную точку того набора явных пользовательских сигналов, на котором анализ был построен.

Минимальный логический контракт:

```text
set_inferred_preferences
  target
  hypotheses
  analysis
    evidence_checkpoint
    evidence_digest
    algorithm_version
```

Если после снимка данных появился новый отзыв, он остаётся неучтённым относительно этой контрольной точки; нельзя просто сбрасывать счётчик в ноль.

## 19. Один основной запуск GitHub Actions для записи данных

Обычная запись данных в v6 проходит один основной запуск GitHub Actions:

```text
PR с запросом
→ получить свежий main
→ проверить, что до исполнения PR содержит только один .media/requests/<id>.json
→ применить типизированный запрос к свежему main
→ проверить запрос и предварительные условия
→ выполнить транзакцию
→ определить и один раз пересобрать только нужные производные данные
→ выполнить итоговую проверку данных
→ закоммитить проверенный результат
→ отправить изменения в ветку PR
→ безопасно слить тот же проверенный head
```

До выполнения операции ветка PR должна содержать только один файл запроса `.media/requests/<id>.json` и не должна содержать заранее подготовленных изменений основных YAML-данных или `media/generated/**`. Это правило уже есть в текущем конвейере и становится явным инвариантом v6.

Так как одновременные независимые пользовательские записи в реальном сценарии отсутствуют, отдельная сложная глобальная очередь для нескольких отзывов не требуется. Слияние обычной операции с данными выполняется через GitHub API в том же основном процессе GitHub Actions после успешной проверки. Прямой push проверенного результата в `main` не используется, а обязательный `--auto` не является частью контракта.

Перед слиянием runner обязан снова прочитать текущий `main` и убедиться, что он совпадает с base SHA, на котором была применена и проверена операция. Если `main` изменился, запрос повторно накладывается на новый `main`, а изменённое состояние заново проходит необходимые проверки. Слияние разрешено только для того head SHA, который был проверен относительно актуального `main`.

Цель нормального пути — один запуск GitHub Actions, одно получение рабочей копии, одна установка Python-зависимостей и один цикл применения и проверки обычной операции. Повторный цикл допускается только как исключительная защита от изменения `main` во время выполнения.

Отдельная полная проверка остаётся для изменений исполняемой логики, схем, процессов GitHub Actions и других архитектурных контрактов.

## 20. Разделение проверок данных и проверок разработки

### Проверки обычных операций с данными

Для обычных записей данных:

- проверка схемы;
- проверка доменных инвариантов и инвариантов операции;
- проверка основных данных;
- проверка разрешённых путей;
- проверка согласованности затронутых производных данных;
- точечные тесты для данного типа операции;
- проверка квитанции операции и идемпотентности.

### Полные проверки разработки

Для Python-кода, схем, процессов GitHub Actions, контракта словаря, архитектурной конфигурации, логики сайта и тестов:

- полный набор `pytest`;
- проверка основных данных;
- полная проверка воспроизводимости пересборки;
- `doctor`;
- проверки сайта;
- проверки согласованности архитектуры и документации.

Результат обычной операции с данными не должен запускать несвязанные тяжёлые проверки разработки. При реализации обязателен аудит всех условий запуска GitHub Actions, включая Media Check, Media Dev Check, Web Check и Media Pages. Нельзя добавлять `paths-ignore` механически: правило должно соответствовать фактическим условиям запуска каждого процесса GitHub Actions.

## 21. PR и слияние в GitHub

Работа через PR сохраняется ради понятной истории изменений, проверки разрешённых путей, диагностики и совместимости с Broker.

Норма:

```text
1 human event
= 1 request PR
= 1 application cycle
= 1 merge
```

Количество технических коммитов внутри ветки не является показателем производительности.

Автоматическое слияние остаётся закрытым по умолчанию и разрешается только при:

- разрешённом типе операции;
- соблюдении правил разрешённых путей;
- успешной итоговой проверке данных;
- подтверждённом соответствии операции и её результата;
- отсутствии неразрешённого конфликта.

## 22. Работа с внешним поставщиком данных

Отзыв о существующем произведении не требует секрета внешнего поставщика и не обращается к нему.

Операция для нового произведения использует внешнего поставщика только для надёжного определения произведения и получения минимально необходимых фактов.

Ошибка при получении необязательных метаданных не должна превращать один пользовательский отзыв в цепочку нескольких операций.

## 23. Web/Broker

LLM и сайт — два клиента одного общего доменного слоя Media.

Ответственности:

```text
Доменный слой Media:
- проверка данных
- защита от устаревшего состояния
- правила истории
- идемпотентность
- изменение основных данных
- определение и пересборка зависимых результатов

LLM:
- понимание естественного языка
- семантический анализ
- разговорный интерфейс
- временное состояние текущего разговора

Broker:
- граница доверия для браузера
- аутентификация и авторизация
- отправка типизированных операций
- получение статуса операции

Сайт:
- отображение данных
- взаимодействие в браузере
- при необходимости показ ожидающего статуса
```

Broker остаётся без собственного состояния. v6 не добавляет D1/KV/Durable Objects или новую серверную базу данных.

Сайт использует для отзывов те же контрольные хэши пользовательских данных, правила идемпотентности и доменную семантику.

Модель чтения сайта показывает только подтверждённое состояние; собственный статус ожидающей операции может отображаться в интерфейсе, но не становится основным состоянием данных.

## 24. Границы кода

`transaction.py` должен остаться тонким координатором.

Логические области v6:

- реестр команд и схем;
- оркестрация записи о произведении;
- пользовательские отзывы;
- идентификация произведения;
- метаданные;
- семантика;
- предпочтения;
- сходство;
- контрольные хэши;
- зависимости и определение устаревших результатов;
- пересборка производных данных;
- транзакция.

Новая составная операция имеет отдельный планировщик, который вызывает независимые доменные функции, но ни одна доменная функция сама не запускает пересборку.

Главная последовательность:

```text
команда
→ доменный планировщик
→ MutationPlan(changed_domains)
→ планировщик зависимостей
→ DirtyPlan
→ транзакция и пересборка
```

Основной путь должен быть понятен без чтения половины `media/`.

### 24.1 Локальный запуск тех же операций

Любая операция записи v6, включая `record_media_entry` и `set_inferred_preferences`, должна полностью выполняться локально через общий загрузчик команд и существующий CLI:

```bash
python -m media.cli apply-command request.json
python -m media.cli apply-command request.json --dry-run
```

GitHub Actions не должны содержать отдельную бизнес-логику, которой нет в локальном пути. Удобную отдельную команду вида `media entry` можно добавить позже только при реальной необходимости.

### 24.2 Хранение данных и SQLite

v6 не добавляет `db.sqlite` ни как основное хранилище, ни как версионируемый производный файл.

Для текущего масштаба медиатеки YAML и небольшие детерминированные производные представления лучше соответствуют требованиям проекта:

- человекочитаемое сравнение изменений в Git;
- простое ревью и восстановление;
- отсутствие бинарного файла, меняющегося при многих записях;
- прямая совместимость с GitHub Pages и текущим Web;
- отсутствие дополнительной синхронизации между YAML и базой.

Существующие `media/tools/build_db.py` и `SQLiteRepository` могут остаться как невёрсионируемый производный инструмент для локальной диагностики, тестов или временного чтения. `doctor` по-прежнему может строить SQLite во временном каталоге. Этот SQLite не входит в основной путь записи или чтения v6, не становится источником состояния и не хранится в Git. Расширять его роль следует только после измерений, если YAML/JSON-путь действительно станет узким местом.

## 25. Обратная совместимость

После перехода на v6 система не обязана бесконечно поддерживать старый API переоценки.

`record_viewing_feedback` может временно остаться узкой командой совместимости поверх новых доменных примитивов, если это почти ничего не стоит и не влияет на архитектуру.

Новый основной маршрут LLM — составная операция v6.

Все незавершённые PR старых операций и старое состояние сессий должны быть завершены или закрыты до перехода.

## 26. Модель ошибок

Обычная запись имеет только следующие значимые состояния:

- `accepted` — запрос принят локально;
- `pending` — сохранение ещё не подтверждено;
- `authoritative` — результат подтверждён в `main`;
- `failed/conflicted` — операция завершилась ошибкой или конфликтом.

Составное пользовательское событие применяется атомарно либо не применяется вообще.

### Конфликт

Конфликт контрольного хэша пользовательских данных приводит к повторному чтению компактного контекста и переоценке исходного намерения пользователя, а не к слепой перезаписи.

### Ошибка внешнего поставщика

Существующее произведение не затрагивается. Новое произведение блокируется только тогда, когда его нельзя надёжно определить.

### Ошибка проверки семантики

Операция отклоняется до изменения основных данных; LLM исправляет содержимое запроса, а повторная отправка сохраняет идемпотентность пользовательского события.

### Временное состояние текущего разговора

Ошибка или конфликт не превращаются в сохранённую историю.

## 27. Квитанции операций

Квитанция остаётся компактным артефактом для аудита:

- operation_id;
- idempotency_key;
- operation;
- status;
- changed_entities;
- changed_domains;
- changed_files;
- applied_at;
- минимальные сведения, специфичные для операции.

Квитанция не дублирует снимок основных данных.

## 28. Проверяемый контракт быстродействия

Скорость становится частью проверяемой корректности системы.

### Существующее произведение + отзыв

Должно выполняться:

```text
обращения к поставщику данных          = 0
повторные расчёты семантики            = 0 при неизменном ключе семантики
обновления метаданных                  = 0
типизированные операции                = 1
PR операции                            = 1
холодные запуски CI для записи данных  = 1
транзакции основных данных             = 1
пересборка каждого нужного результата <= 1
слияние                                = 1
```

### Новое произведение

```text
этап определения произведения и получения фактов = 1
проход LLM для семантики                         = 1
типизированные операции                          = 1
транзакции основных данных                       = 1
пересборка каждого нужного результата           <= 1
цикл CI для записи данных                         = 1
слияние                                           = 1
```

Фактическое время выполнения используется как диагностический показатель, а не как хрупкое условие прохождения CI. Структурные причины задержки должны проверяться напрямую.

## 29. Набор обязательных сценариев проверки

Минимальный постоянный набор сценариев:

1. существующее произведение — только оценка;
2. существующее произведение — подробный отзыв;
3. существующее произведение — исправление статуса просмотра;
4. существующее произведение — семантика не изменилась;
5. существующее произведение — исправление семантики;
6. новое произведение — только статус просмотра;
7. новое произведение — оценка и подробный отзыв;
8. отзыв `partner`;
9. устаревший контрольный хэш пользовательского состояния;
10. идемпотентный повтор операции;
11. результат `no_change`;
12. порог анализа вкусов ещё не достигнут;
13. порог анализа вкусов достигнут;
14. рекомендация для пары, когда повторный анализ нужен только одному участнику;
15. одинаковый результат одной и той же пользовательской операции через LLM и Broker.

Каждый сценарий проверяет итог основных данных, изменившиеся области, набор пересборок, допустимые внешние обращения и класс CI-проверки.

## 30. Эталонные данные для проверки качества рекомендаций

После сброса активная пользовательская библиотека не используется как регрессионный тестовый набор.

Создаются синтетические и эталонные тестовые наборы для:

- сильных положительных сигналов к интриге и решению задач;
- смешанных сигналов;
- различий во вкусах пары;
- слабого покрытия семантическими данными;
- явно указанного сходства без превращения его в предпочтение;
- устаревшего выведенного профиля при наличии свежих явных сигналов, которые ему противоречат.

Регрессионные тесты защищают качественные инварианты, а не старый персональный набор данных.

- `media/README.md`;

- `broker/README.md`;
- `web/README.md`;

Правило:

> Код, схемы, тесты, действующая документация, маршрутизация агента и контракт Web/Broker должны описывать одну и ту же семантику v6.

Английские термины сохраняются, когда это имя конкретного API, файла, команды, класса или когда русский перевод делает смысл менее точным. При первом использовании сложного термина нужно кратко объяснять его простыми словами.

Исторические спецификации v5/v5.1 задним числом не переписываются. Эта спецификация после перехода явно заменяет старый рабочий процесс переоценки; действующая документация меняется только вместе с работающей реализацией v6.

### 31.1 Контрольные точки разработки в PR

Во время реализации каждый крупный PR должен регулярно сохранять понятную контрольную точку, чтобы работу можно было безопасно продолжить после паузы или в другой сессии.

После каждого значимого этапа и обязательно перед паузой в PR обновляется текущий статус — в описании PR или в отдельном верхнеуровневом комментарии:

- что уже сделано;
- какой коммит или текущая вершина ветки (head) является контрольной точкой;
- какие проверки уже прошли;
- что сейчас не закончено или известно как риск;
- следующий конкретный шаг;
- краткий план оставшейся работы.

Контрольная точка не заменяет небольшие логические коммиты. Её задача — оставить достаточно контекста для точного возобновления работы без повторного исследования всего PR.

## 32. Атомарный переход на v6

v6 не вводится как длительный гибрид старой и новой архитектуры.

До перехода на v6 должны быть готовы:

- детерминированный генератор MD-архива и режим проверки его точного соответствия текущим основным данным;
- реализация команд и доменной логики v6;
- новые контрольные хэши и правила определения устаревших данных;
- основной путь записи данных через один запуск GitHub Actions;
- совместимость Broker и сайта;
- контрольные точки и правила повторного анализа вкусов;
- тесты быстродействия и качества;
- генератор архива и проверка его полноты;
- обновлённая действующая документация.

Непосредственно перед удалением старых данных финальный MD-архив заново генерируется из точного состояния `main`, которое будет сброшено. Проверка должна сравнивать зафиксированный архив с повторно сгенерированным результатом, а не только количество произведений. Деструктивный сброс запрещён, если проверка не завершилась успешно.

Один переход включает:

- человекочитаемый архив;
- сброс активных данных;
- удаление старого рабочего процесса;
- чистое производное состояние;
- код, процессы GitHub Actions и документацию v6;
- совместимые Broker и сайт.

## 33. Откат

История Git остаётся технической резервной копией.

До появления новых пользовательских данных v6 переход можно откатить контролируемым `revert`.

После появления новых отзывов v6 слепой откат запрещён, потому что он уничтожит новые пользовательские данные. В этом случае восстановление выполняется только новой миграцией вперёд.

## 34. Проверки сразу после перехода

Сразу после сброса должно быть доказано:

- в основных данных нет произведений;
- подборки пусты;
- связи сходства пусты;
- взаимодействия пусты;
- старый пилот отсутствует;
- выведенные профили пусты и согласованы с пустой медиатекой;
- глобальные явно заданные предпочтения сохранены;
- производное состояние воспроизводимо;
- сайт корректно отображает пустую медиатеку;
- новый фильм можно добавить по полному рабочему пути;
- после первого добавления работает быстрый путь для существующего произведения;
- ограничения рекомендаций на пустой или почти пустой библиотеке объясняются корректно.

## 35. Что сознательно не входит в v6

В v6 сознательно не входят:

- внешняя база данных;
- новый отдельный серверный сервис;
- Cloudflare KV/D1/Durable Objects;
- отдельный фоновый процесс LLM;
- фоновый демон семантической обработки;
- полная перепись Web;
- отказ от Git/YAML;
- сложный частичный пересчёт профиля до появления измеримого узкого места;
- универсальный механизм произвольных пакетных транзакций;
- автоматическое восстановление старых выведенных предпочтений;
- автоматический импорт MD-архива обратно в систему анализа;
- пакетное восстановление старых пользовательских сигналов из MD-архива в обход полного сброса;
- сохранение старой подсистемы переоценки как рабочего пути.

## 36. Условия готовности v6

v6 считается готовой только когда одновременно выполнены четыре группы условий.

### Быстродействие

Обычный отзыв о существующем произведении не должен без доказуемой необходимости вызывать внешние обращения, обновление метаданных, повторный расчёт семантики, несколько циклов транзакции/пересборки или несколько тяжёлых CI-задач.

### Качество

Все инварианты качества анализа v5.1, перечисленные в этой спецификации, проходят регрессионные тесты.

### Чистый переход

Старые пользовательские данные сохранены в MD-архиве, старый рабочий процесс удалён, активная медиатека очищена, глобальные явно заданные предпочтения сохранены.

### Совместимость

LLM работает как основной быстрый интерфейс, а сайт через Broker остаётся рабочим вторичным клиентом той же системы основных данных.

## 37. Итоговый принцип

> **Каждый тяжёлый шаг выполняется максимум один раз и только тогда, когда изменение его входных данных доказывает необходимость. Качество анализа и рекомендаций сохраняется как обязательный инвариант, а не как пожелание.**
