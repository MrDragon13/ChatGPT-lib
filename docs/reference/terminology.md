# Термины

Короткий словарь для живой документации, code review и работы агента. Там, где в коде используется английское имя, оно сохранено в обратных кавычках.

## Канонические данные — `canonical`

Долговременные данные и контракты, которые считаются источником истины. Для media это в первую очередь YAML, настройки, предпочтения, связи, схемы и словарь.

## Производные данные — `derived`

Представления, которые детерминированно строятся из канонических данных: индекс, профиль, `taste_context`, временная SQLite-база, Web manifest и другие read models.

Их можно пересобрать. Нельзя менять их вручную, чтобы обойти изменение канонических данных.

## Произведение — `work`

Фильм, сериал или другое произведение в медиатеке с устойчивым локальным ID, identity, метаданными, пользовательскими сигналами и при наличии semantic fingerprint.

## `WorkRef`

Ссылка на произведение. Может указывать на локальный `work_id` или на устойчивую внешнюю identity провайдера.

Используется там, где операция должна говорить о произведении, которое не обязательно уже добавлено в медиатеку.

## Контекст данных — `target`

Определяет, чьи субъективные данные читаются или записываются. Основные значения:

- `primary`;
- `partner`;
- `couple`.

## Явный зрительский сигнал — `viewer signal`

Данные, которые принадлежат пользователю напрямую: просмотр, оценка, реакция, отзыв и связанные поля.

## Явное предпочтение — `explicit preference`

Устойчивое предпочтение или ограничение, которое пользователь сообщил напрямую и которое имеет смысл помнить долго.

## Выведенная гипотеза — `inferred hypothesis`

Вывод о вкусе на основе независимых явных сигналов. Такой вывод не считается новым независимым доказательством сам для себя.

## Семантический профиль — `semantic fingerprint`

Описание самого произведения через контролируемый словарь: структура истории, тон, опыт просмотра и другие признаки. Не является оценкой пользователя.

## Основание — `evidence`

Конкретная причина для вывода: явное предпочтение, отзыв, повторяющаяся независимая закономерность, характерное произведение, interaction или явно указанное сходство.

Происхождение данных должно позволять отличить слова пользователя от выведенной гипотезы.

## `taste_context`

Компактный read model для рассуждения о вкусе: явные и выведенные данные, характерные произведения, свежие отзывы, исключения, affinity, similarity и разногласия пары.

## `recommend_context`

Read model, который соединяет вкусовой контекст с набором кандидатов и ограничений для объяснимой рекомендации.

## `assess_candidate`

Read-only оценка конкретного кандидата: качественный вывод, уверенность, сильные стороны, риски и основания. Результат не сохраняется как факт о вкусе.

## Явное сходство — `explicit similarity`

Пользовательское утверждение «A похож на B» для конкретного `target`.

Связь симметрична, хранится отдельно от фактических отношений sequel/prequel/remake и может помогать рекомендациям, но сама по себе не является предпочтением.

## Вычисленное сходство — `derived similarity`

Сходство, полученное из semantic fingerprints или model reasoning. Не становится пользовательским утверждением без явного подтверждения.

## `reconciliation`

Детерминированная замена сохранённой внешней identity на локальный `work_id`, когда произведение позже появляется в медиатеке.

Она нормализует ссылки, но не создаёт новые зрительские сигналы.

## Типизированная операция — `typed operation`

Строгий JSON-запрос, который соответствует схеме и обрабатывается определённым handler/read builder.

Write-операции меняют данные через контролируемый путь. Read-only операции только возвращают контекст.

## Обычная операция данных — `normal data operation`

Поддерживаемое пользовательское изменение, которое при выполнении всех проверок может автоматически слиться в `main`.

## Операция обслуживания — `maintenance operation`

Более широкое техническое изменение данных, например массовый `refresh_metadata`, которое требует ручного review.

## Developer PR

Обычный PR для изменений кода, схем, словаря, архитектуры, workflows, тестов и документации. Он не получает права обычной auto-merge операции данных.

## Broker

Защищённый server-side слой для разрешённых записей из браузера. Он скрывает секреты и использует общий typed-operation путь.

## Web manifest

Версионированный производный JSON для статического Web. Это не самостоятельное хранилище данных.

## Живая документация — `living docs`

Документы, которые описывают текущее поведение, использование, эксплуатацию и контракты. Они обновляются вместе с реализованным изменением.

## История решений

Датированные specs/plans в `docs/superpowers/`. Они объясняют, почему система пришла к текущему виду, но не переопределяют код, схемы, `AGENTS.md` и живую документацию.

## Устойчивый статус — `durable status`

Короткое описание текущих возможностей и известных ограничений без временного журнала конкретного PR, ветки или CI-run.
