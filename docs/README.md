# Документация ChatGPT-lib

Текущая media-подсистема — **Media Intelligence v6**.

Здесь собрана живая документация: то, как проект устроен и работает сейчас. Датированные specs/plans в `docs/superpowers/` и записи в `docs/archive/` сохраняются как история решений и не заменяют текущие правила.

## Быстрый маршрут

- [Общая архитектура](architecture/overview.md) — основные части системы и границы ответственности.
- [Как пользоваться медиатекой](guides/media-usage.md) — обычные пользовательские сценарии.
- [Разработка](guides/development.md) — ветки, тесты, PR и правила изменения контрактов.
- [Эксплуатация](guides/operations.md) — проверка, пересборка, публикация и восстановление.
- [Операции media](reference/media-commands.md) — список команд и их назначение.
- [Текущее состояние](status/current.md) — устойчивые возможности и известные ограничения.

## Что считать авторитетным

Если нужно понять, что система **реально делает**, сначала смотрите код, JSON Schema, словарь, workflows и исполняемые тесты. Документация должна им соответствовать; расхождение считается ошибкой документации.

Для поведения агента действуют два файла:

- `../AGENTS.md` — маршрутизация на уровне репозитория;
- `../media/AGENTS.md` — основной рабочий договор media-подсистемы.

Они задают обязательные правила работы. Остальная документация объясняет устройство и причины решений, но не ослабляет эти правила.

## Структура живой документации

- `architecture/` — как система устроена;
- `guides/` — как ей пользоваться, разрабатывать и обслуживать;
- `reference/` — короткие технические справочники;
- `status/` — текущее устойчивое состояние;
- `archive/` — завершённые разовые процедуры и исторические записи;
- `superpowers/` — датированные проектные решения и планы.

## Стиль документации

Пишем простым русским разговорно-техническим языком. Английские слова оставляем только там, где это имя команды, поля, файла, продукта или устоявшийся технический термин, который полезно искать в коде. Если термин можно без потери смысла сказать по-русски, говорим по-русски.

Не дублируем один и тот же контракт в нескольких местах. Подробности должны жить в документе, который отвечает за эту тему.

## Что обновлять при изменениях

| Что изменилось | Где обновить документацию |
| --- | --- |
| типизированная операция | `reference/media-commands.md`; при изменении смысла — нужный файл в `architecture/` |
| схема или доменный инвариант | `architecture/media-model.md` и/или `reference/invariants.md` |
| вкус, рекомендации, assessment | `architecture/intelligence.md`; пользовательское поведение — `guides/media-usage.md` |
| запись, CI, автоматическое слияние | `architecture/write-pipeline.md`, `guides/operations.md` |
| manifest, Broker, безопасность | `architecture/web-and-broker.md`; при изменении продукта — `../PRODUCT.md` |
| структура репозитория | `reference/repository-layout.md` |
| внешний вид Web | `../DESIGN.md` |
| текущая возможность или ограничение | `status/current.md` |
| новое архитектурное решение | датированный spec в `superpowers/specs/`, после реализации — соответствующие живые документы |

Если поведение изменилось, а нужная документация не обновлена, это обычная регрессия, а не необязательная косметика.
