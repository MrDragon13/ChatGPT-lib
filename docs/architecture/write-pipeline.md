# Путь записи media-данных

Обычная пользовательская запись не меняет канонические YAML напрямую. Сначала создаётся типизированный запрос, затем доверенный GitHub Actions runner применяет его к свежему `main`.

## Главный принцип

Для обычной записи действует схема:

> одно человеческое событие → один typed request → один operation PR → одна deterministic transaction → минимальная пересборка → одна проверка → одно слияние.

GitHub остаётся границей долговременного сохранения, но разговор с пользователем не должен ждать весь цикл записи.

## Request-only PR

Обычная запись создаёт ветку `media/op-*` от текущего `main`.

До выполнения операции PR содержит ровно один файл:

```text
.media/requests/<operation-id>.json
```

Клиент заранее не готовит изменения канонических YAML или `media/generated/**`. Их создаёт доверенный runner, повторно применяя исходный intent к свежему `main`.

Так операция переигрывается на актуальных данных вместо слияния устаревшего готового diff.

## Очередь

Обычные записи сериализуются GitHub Actions:

```yaml
concurrency:
  group: media-data-pipeline
  cancel-in-progress: false
  queue: max
```

Отдельная база блокировок или сервис очереди не используются.

Очередь уменьшает риск параллельных записей, но не заменяет финальную проверку базы: `main` может измениться из-за developer/manual PR.

## Единый `Media Command` runner

Для `execution_class=v6_single_runner` один runner выполняет весь путь:

1. принимает request как недоверенные входные данные;
2. получает свежий `origin/main`;
3. убеждается, что исходный PR содержит только request;
4. заново строит operation branch от свежего `main`;
5. проверяет JSON Schema и preconditions;
6. выполняет deterministic transaction;
7. вычисляет `changed_domains` и `DirtyPlan`;
8. пересобирает каждый нужный производный результат максимум один раз;
9. проверяет `media/config/operation_path_policy.json`;
10. запускает каноническую валидацию, `rebuild --check` и тесты этой операции;
11. коммитит проверенный результат;
12. ещё раз читает текущий `main`;
13. если база изменилась, повторяет replay ограниченное число раз;
14. если база та же, GitHub API сливает exact checked head;
15. `Media Pages` запускается для точного merge SHA.

Прямой `git push HEAD:main` не используется.

## Что проверяется для обычной записи

Обычная media-операция не запускает весь developer regression suite. Её проверка должна доказать корректность именно этой записи:

- JSON Schema и команда;
- preconditions;
- каноническая валидация;
- разрешённые пути;
- минимальная пересборка;
- `rebuild --check`;
- целевые тесты операции;
- receipt и idempotency.

Полный pytest, doctor и Web/Broker-проверки остаются обязательными для developer changes.

## Классы исполнения

Источник истины — `media/config/operation_path_policy.json`.

- Все операции с `auto_merge=true` используют `execution_class=v6_single_runner`.
- Bulk `refresh_metadata` использует `execution_class=manual_review`: workflow может подготовить и проверить изменения, но не сливает их автоматически.
- Код, схемы, словарь, workflows и архитектура меняются обычным developer PR.

Старый раздельный validation/merge path удалён; текущий путь обычной записи обслуживает единый `Media Command` runner.

## Доступ к провайдеру

Секрет провайдера передаётся только операции, которой действительно нужны внешние данные.

Запись отзыва о существующем произведении не требует provider I/O.

Для нового `record_media_entry(create_if_missing=true)` доверенный код проверяет устойчивую identity и получает актуальные фактические метаданные. Клиент не передаёт эти метаданные как блокирующее условие.

## `record_media_entry`

Это основной v6-путь для события «пользователь сообщил что-то об одном произведении».

### Уже известное произведение

Payload обычно содержит:

- `work_ref`;
- `target_updates`;
- `preconditions.expected_viewer_digests`.

Метаданные и semantics при этом не обновляются.

### Новое произведение

Payload дополнительно содержит:

- `creation_context.provider_identity`;
- `semantic_snapshot.traits`;
- пользовательские изменения.

Актуальные metadata, `semantic input digest`, `vocabulary digest` и `algorithm version` вычисляет доверенный runtime.

Произведение, semantic fingerprint и пользовательские сигналы создаются одной transaction.

Если при `create_if_missing=true` произведение уже найдено по устойчивой identity, его существующие metadata/semantics не перезаписываются creation payload.

## Idempotency

`operation_id` относится к технической попытке. `idempotency_key` — к одному пользовательскому событию.

Повтор с тем же ключом и тем же нормализованным запросом возвращает уже применённый результат. Тот же ключ с другим intent завершается ошибкой.

`no_change` — нормальный успешный результат: он не создаёт искусственную историю и не запускает лишнюю пересборку.

## Пока запись ещё выполняется

LLM может продолжать разговор и учитывать свежий явный сигнал локально.

Если пользователь уточняет то же произведение до завершения первой записи, второй Git request не отправляется. Уточнение остаётся в текущей сессии. После завершения первой операции агент заново читает `media_entry_context`, получает свежий viewer digest и отправляет следующую операцию.

Web делает то же: не отправляет второй submit, но сохраняет локальный черновик.

## Разрешённые пути и безопасность

`media/config/operation_path_policy.json` определяет, какие пути может менять каждая операция.

Обычная запись не получает права менять схемы, словарь, workflows, правила агента или архитектуру.

`Media Command` выполняет защищённый путь только для same-repository PR `media/op-*`. Fork и недоверенные PR не получают выполнение с секретами.

Если меняются правила доступа к репозиторию, branch protection/rulesets или модель доверия, нужен отдельный security review.

## Read-only операции

`media_entry_context`, `recommend_context`, `taste_context` и `assess_candidate` не создают operation PR и не меняют канонические данные.

## Pages

После merge `Media Pages` получает точный merge SHA и заново строит Web manifest.

Публикация более раннего зелёного commit не считается публикацией текущего состояния.

## Developer changes

Изменения Python, схем, workflows, словаря, архитектуры/config и Web/Broker-кода проходят обычный PR и полный набор релевантных проверок. Для них normal media auto-merge не используется.
