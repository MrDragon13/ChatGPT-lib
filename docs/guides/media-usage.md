# Как пользоваться медиатекой

Этот guide описывает пользовательские сценарии. В обычном разговоре не нужно думать о GitHub, YAML, ветках или Actions: агент сам выбирает безопасный typed route. Технические имена операций приведены здесь только как reference поведения.

## Контексты: Я, партнёр, вместе

Система различает три target:

- `primary` — основной пользователь;
- `partner` — партнёр;
- `couple` — совместный group context.

Если target понятен из разговора, агент использует его без лишнего опроса. Если это влияет на смысл и неясно — уточняет только необходимое. Данные разных targets не копируются друг в друга молча.

## Записать просмотр и впечатления

Можно сказать естественно:

- «Посмотрел Arrival, 9/10, очень понравилась атмосфера»;
- «Мы вместе посмотрели фильм, нам скорее понравилось»;
- «Она посмотрела X и поставила 7».

Обычный route — `record_media_entry`. Viewing, rating, reaction и текстовый feedback независимы: отсутствие оценки не означает отсутствие просмотра или негативную реакцию.

Если work ещё не в библиотеке и пользователь одновременно сообщает просмотр/feedback, система использует create-if-missing flow в рамках той же операции: stable provider identity проверяется один раз, а provider metadata и semantic bookkeeping вычисляются на trusted side.

## Исправить или удалить часть feedback

Для исправления уже записанного сигнала используется `edit_viewing_feedback`. Clear одного поля не должен стирать соседние данные. Destructive purge — отдельное явное действие.

Примеры:

- «Поменяй мою оценку X на 8»;
- «Удали только текстовый отзыв, оценку оставь»;
- «Я ошибся, это смотрела партнёрша, а не я» — здесь важна target safety; агент не должен молча переносить данные без корректного route.

## Interest

`set_interest` хранит устойчивое состояние интереса к произведению. Временное «не сегодня» не должно автоматически становиться постоянным `not_interested`.

## Рекомендации

### Из своей медиатеки

Фраза вроде «что посмотреть из моей медиатеки?» означает internal candidate boundary: рассматриваются локальные works.

### Общая рекомендация

Обычная просьба «посоветуй фильм» использует external discovery по умолчанию. Локальная библиотека служит памятью о вкусах, evidence и exclusions, но не ограничивает кандидатов только уже добавленными works.

Сам факт рекомендации внешнего фильма **не добавляет его в медиатеку**.

## «Понравится ли мне конкретный фильм?»

Для этого есть read-only `assess_candidate`.

Кандидат может:

- уже быть canonical work;
- быть `external` фильмом, которого ещё нет в библиотеке.

Assessment использует taste evidence, semantic traits, concrete liked/disliked works и explicit similarity. Он возвращает qualitative вывод и confidence с причинами/рисками, а не fake precise probability.

Важный инвариант: external candidate можно оценить **не добавляя его в медиатеку**. Сам assessment ничего не записывает.

## Сказать, что два фильма похожи

Фраза вроде «Дежавю похож на Исходный код» создаёт explicit target-specific similarity через `set_work_similarity`.

Similarity:

- undirected: A↔B и B↔A — одна связь;
- может иметь structured reasons + optional note;
- относится к конкретному `primary`, `partner` или `couple`;
- может ссылаться на `external` work, которого ещё нет в библиотеке;
- является evidence/hint для будущих рекомендаций и объяснений, но сама по себе не становится preference.

Если второй фильм ещё не добавлен, система сохраняет stable external identity; это **не добавляет фильм в медиатеку**, не создаёт просмотр, rating или interest. Когда work позже реально появится, relation может быть детерминированно reconciled к canonical ID.

Чтобы убрать мнение о сходстве: «Я больше не считаю A похожим на B» → `remove_work_similarity`.

## Переанализировать вкус

Запрос вроде «переосмысли мой вкус по всей истории» строит свежий taste context и может заменить inferred hypotheses через `set_inferred_preferences`.

Inferred conclusions не должны подтверждать сами себя. Explicit feedback и независимые повторяющиеся сигналы остаются важнее предыдущего inferred output.

## Обновить понимание произведения

Semantic enrichment через `set_semantic_fingerprint` описывает сам work, а не реакцию пользователя. Если подходящего controlled vocabulary term нет, агент не придумывает новый термин скрыто в процессе обычной записи.

## Что не сохраняется автоматически

Без явного устойчивого заявления не становятся permanent preference:

- текущий mood;
- runtime constraint для сегодняшнего вечера;
- «не сегодня»;
- одноразовый контекст компании/жанра;
- prediction из `assess_candidate`;
- автоматически выведенная semantic similarity.

## Когда появляется technical detail

GitHub/PR/validation детали обычно скрыты. Они нужны пользователю только если operation не удалось завершить, возникла ambiguity, требуется manual architecture/maintenance change или пользователь сам попросил технические подробности.
