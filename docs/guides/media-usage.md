# Как пользоваться медиатекой

В обычном разговоре не нужно думать о GitHub, YAML, ветках и Actions. Агент сам выбирает безопасную операцию. Технические имена ниже нужны только для ясности и поиска по документации.

## Я, партнёр, вместе

Система различает:

- `primary` — я;
- `partner` — партнёр;
- `couple` — мы вместе.

Если из разговора понятно, чьи данные обсуждаются, агент не задаёт лишних вопросов. Если это действительно неясно и влияет на смысл, он уточняет только необходимое.

Данные разных контекстов не копируются друг в друга молча.

## Записать просмотр, оценку или отзыв

Можно говорить естественно:

- «Посмотрел Arrival, 9/10, очень понравилась атмосфера»;
- «Мы вместе посмотрели фильм, нам скорее понравилось»;
- «Она посмотрела X и поставила 7».

Основная операция — `record_media_entry`.

Просмотр, оценка, реакция и текстовый отзыв независимы. Например, фильм можно отметить просмотренным без оценки.

Если произведения ещё нет в библиотеке, та же операция может создать его: сначала надёжно проверяется устойчивый ID провайдера, затем доверенный код получает фактические метаданные, а семантические признаки передаются из контролируемого словаря.

## Исправить или удалить часть данных

Для точечного изменения уже записанного отзыва используется `edit_viewing_feedback`.

Очистка одного поля не должна стирать соседние данные. Полное удаление — отдельное явное действие.

Примеры:

- «Поменяй мою оценку X на 8»;
- «Удали только текстовый отзыв, оценку оставь»;
- «Я ошибся, это смотрела партнёрша, а не я» — здесь важно не перенести данные между `target` молча.

## Интерес

`set_interest` хранит устойчивое отношение к произведению.

Фраза «не сегодня» сама по себе не должна превращаться в постоянное `not_interested`.

## Рекомендации

### Только из своей медиатеки

Фраза «что посмотреть из моей медиатеки?» ограничивает кандидатов локальными произведениями.

### Обычная рекомендация

Фраза «посоветуй фильм» по умолчанию допускает внешний поиск.

Локальная библиотека помогает понять вкус, помнить уже просмотренное и исключать неподходящее, но не ограничивает список только тем, что уже добавлено.

Сам факт рекомендации внешнего фильма **не добавляет его в медиатеку**.

## Понравится ли мне конкретный фильм?

Для этого используется read-only операция `assess_candidate`.

Кандидат может уже быть в медиатеке или оставаться внешним. Ответ опирается на вкус, семантические признаки, конкретные понравившиеся/не понравившиеся фильмы и явно указанное сходство.

Результат — качественный вывод с причинами и рисками, а не псевдоточная вероятность.

Сам `assess_candidate` ничего не записывает и не добавляет внешний фильм в медиатеку.

## Два фильма похожи

Фраза «Дежавю похож на Исходный код» сохраняет явное сходство через `set_work_similarity`.

Такая связь:

- симметрична;
- относится к конкретному `primary`, `partner` или `couple`;
- может включать причины и заметку;
- может ссылаться на внешний фильм;
- помогает рекомендациям, но сама по себе не становится предпочтением.

Внешний фильм при этом не добавляется в библиотеку и не получает просмотр, оценку или интерес.

Чтобы убрать связь, используется `remove_work_similarity`.

## Переанализировать вкус

Фраза «переосмысли мой вкус по всей истории» строит свежий `taste_context` и при необходимости сохраняет новые выведенные гипотезы через `set_inferred_preferences`.

Старые выводы не должны подтверждать сами себя. Явные пользовательские сигналы всегда важнее.

## Обновить семантику произведения

`set_semantic_fingerprint` меняет описание самого произведения, а не отношения пользователя к нему.

Если нужного термина нет в контролируемом словаре, обычная запись не должна незаметно добавлять новый термин.

## Что не становится постоянным предпочтением автоматически

Без явного устойчивого заявления не сохраняются как долгосрочное правило:

- настроение на сегодня;
- ограничение по длительности только на один вечер;
- «не сегодня»;
- случайный контекст компании;
- прогноз из `assess_candidate`;
- автоматически вычисленное сходство.

## Когда показывать технические детали

Обычно GitHub/PR/validation остаются за кадром. Технические подробности нужны, если операция не удалась, возникла неоднозначность, требуется ручное изменение архитектуры или пользователь сам попросил детали.
