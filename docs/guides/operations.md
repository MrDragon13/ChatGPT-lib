# Эксплуатация и проверка

Короткое руководство по проверке, пересборке, публикации и восстановлению. Если не сказано иначе, команды запускаются из корня репозитория.

## Python-зависимости

```bash
python -m pip install -r media/requirements.txt
```

## Полная проверка медиатеки

```bash
python -m pytest -q
python -m media.tools.validate .
python -m media.cli rebuild --check
python -m media.cli doctor --format json
```

Что проверяет каждая команда:

- `pytest` — исполняемые контракты;
- `validate` — схемы и инварианты канонических данных;
- `rebuild --check` — совпадают ли сохранённые производные файлы с тем, что должно быть построено из канонических данных;
- `doctor` — целостность репозитория и среды выполнения.

Нельзя считать изменение разработчика полностью проверенным, если прошёл только один целевой тест, а полный набор проверок падает.

## Пересборка производных данных

Если нужно не только проверить, но и пересобрать:

```bash
python -m media.tools.build_index media
python -m media.tools.build_profiles media
python -m media.tools.build_db media
```

`generated/database.sqlite` — временный пересобираемый файл, а не источник истины.

После пересборки снова выполните проверку, `rebuild --check` и doctor.

## Web manifest

Ручная проверка экспорта:

```bash
python -m media.cli web-export --output /tmp/media-web-manifest.json --format json
```

Текущий контракт описан в `docs/architecture/web-and-broker.md`. Фактическая версия определяется кодом экспортёра/schema.

## Проверка Web

```bash
cd web
npm ci
npm run test:run
npm run typecheck
npm run build
```

Если меняется поведение браузера или внешний вид, дополнительно нужны проверки Playwright в браузере и сканирование статической сборки по текущему `.github/workflows/web-check.yml`.

## Быстрая проверка канонических данных

```bash
python -m media.tools.validate .
```

Если проверка падает, исправляйте причину в канонических данных, схеме или коде. Не правьте производный файл вручную, чтобы скрыть ошибку.

## Массовое обновление метаданных

Массовый `refresh_metadata` со scope `all_movies` — ручная операция обслуживания.

Она должна:

- сначала проверить идентичности всех затронутых произведений;
- сохранить пользовательские сигналы и ручные переопределения;
- не оставлять частично обновлённые данные при неоднозначности или сбое провайдера;
- пройти ручную проверку и слияние.

`refresh_metadata` не относится к обычным операциям с автоматическим слиянием.

## Основные GitHub Actions

- `Media Command` — применяет обычную типизированную операцию к свежему `main`, проверяет её и сливает точную проверенную вершину ветки;
- `Media Dev Check` — полная проверка медиатеки для PR разработчика;
- `Web Check` — тесты, `typecheck`, сборка, проверки браузера и безопасности Web;
- `Broker Check` — тесты и `typecheck` Broker;
- `Media Pages` — сборка и публикация Pages для точного SHA;
- `Broker Deploy` — ручная публикация Worker с проверкой ожидаемого SHA.

Важно не название процесса GitHub Actions, а то, что успешная проверка относится к той же точной версии, которую собираются сливать или публиковать.

## Проверка Pages после слияния

1. Убедитесь, что `main` указывает на ожидаемый SHA слияния.
2. Найдите `Media Pages` для этого SHA.
3. Проверьте успешную сборку.
4. Проверьте успешную публикацию.
5. При изменении интерфейса проверьте опубликованный сайт.

Пока публикация для SHA слияния не завершилась успешно, текущую версию нельзя считать опубликованной.

## Публикация Broker

`Broker Deploy` запускается вручную из `main`.

В `expected_sha` передаётся точный SHA, который уже прошёл проверки. Процесс повторно сверяет SHA, устанавливает зависимости, запускает тесты Broker и `typecheck` и только затем вызывает `wrangler deploy`.

Если код Broker не менялся, повторная публикация не требуется.

## Расхождение производных файлов

Симптом: проверка канонических данных проходит, но `rebuild --check` показывает расхождение.

Порядок действий:

1. убедитесь, что изменение канонических данных было намеренным;
2. выполните детерминированную пересборку;
3. не вносите ручные смысловые правки в `generated/`;
4. снова запустите полную проверку медиатеки.

Если пересборка неожиданно меняет несвязанные файлы, сначала найдите причину.

## Возобновление прерванной работы

1. Проверьте текущий `main`.
2. Найдите активный PR/ветку.
3. Прочитайте последнюю контрольную точку PR.
4. Сверьте точный SHA вершины ветки и состояние CI.
5. Продолжайте с первого незавершённого шага.

Устойчивое состояние проекта описано в `docs/status/current.md`, а временный прогресс — в активном PR.

## Сбой провайдера

Если провайдер недоступен или идентичность неоднозначна, не угадывайте. Операция должна остановиться до частичной записи или вернуть корректный статус, предусмотренный её контрактом.

## Когда нужен отдельный разбор сбоя

Сначала ищите причину, а не подгоняйте тест под результат, особенно если:

- ошибка появляется только в CI;
- `generated/` расходится с каноническими данными;
- процесс GitHub Actions проверяет не тот SHA;
- сборка для браузера содержит похожие на секреты строки;
- провайдер неоднозначно определяет произведение.
